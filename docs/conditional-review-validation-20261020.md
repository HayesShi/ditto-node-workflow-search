# 条件检查修订与历史错误样本验证

## 结论

工程编排已实现并验证，但不能宣布 checker 误判已经修好。
通过检查时交付原解，不调用 revise；检查不通过才修订，修订目标明确指向原 solver。
节点提示词、工具能力、官方评分器保持不变。这是可搜索的候选组织，不是所有流程的固定后缀。

## 代码变化

- OrganizationSpec 新增可选 outputByGraph，显式声明结束分支交付哪个节点的答案。
- 静态检查要求该答案在所有进入路径上可用；禁止用仅可选产生答案的 checker 作为分支交付来源。
- 执行器按实际结束分支取答案，绑定参与组织哈希和执行身份。
- 提供 conditionalMathReview 示例：solve → check → accept 或 repair。
- accept 原样交付 solver；repair 的 fixer.targetNodeId 明确为 solver，checker 输出仍作为建议输入。
- 新搜索提示词说明该组织方式，同时保留直接解答、独立验证、选择/合并等组织选择。
- 协议升级到 v13-branch-delivery。历史正式记录不变，不能拿旧搜索直接进入新版 Test。

## 三道误改题的完整调用追踪

为16、17、98另做一次固定原解的真实复核，完整保存每次模型请求和响应。
原解3/3正确，最终0/3正确：16的fixer格式失败；17改为D；98改为1/19。
三题的checker均错误判为不通过，因此都进入修订分支。
16的fixer甚至声称“per the supplied evidence the expected answer is 20”。
这是模型自己产生的错误说法：请求中没有官方参考答案，checker的20也不是评分器提供的证据。
说明显式绑定和条件分支虽已正确，模型仍可能把检查建议误当成权威依据。
本次未据此修改通用节点提示词或添加按题号纠错逻辑。
