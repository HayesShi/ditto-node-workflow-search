## 工程修复

### 动作历史缺失

之前 BFCL 后续模型输入只有 `Actual last executed interface: bfcl_call` 和 observations，业务函数名与参数未进入历史。文件题的末次输入有二十多条 user 观察、0条 assistant 决策。此前将重复调用主要归因于模型判断并不完整，确有信息传递缺口。

现将实际执行的 `{done:false,tool,arguments}` 作为 assistant 记录，与真实观察成对传给下一次模型。不把宿主默认 finalAnswer 冒充模型原文；不伪造执行、不拦截重复调用、不用缓存替代真实工具。相同业务参数与相同返回值会反馈重复次数。BFCL 快照替换保留未被原生历史记录的错误对；Automation 使用独立 tool-history，不能依据业务正文中的 complete 字段自动结束。

`None` 保持原样。官方 echo 写文件成功本来可以返回 None，提示仅解释它可能是无返回值，不把 None 一律标为成功。模型可依据公开 schema 或真实核验操作判断。

### 代码答案提取超时

MBPP baseline 两份已生成答案遇到可信 AST 辅助进程5秒启动期限，评测无效。已将该辅助解析器单次启动/分析保护改为30秒，只对 ETIMEDOUT 重试一次，最多两次；JSON/协议/其他进程异常不吞掉。没有重试模型生成，没有执行源代码做分类，没有改变 Docker 内候选程序期限或私有断言。

修复后只对保存的 MBPP 答案重评分：两版各8/8有效，原基线7/8、人工版6/8。没有为恢复评分新增模型调用。重评分脚本同时更新总体状态，避免各组恢复后仍残留 completed-with-blockers。

### 时间限制测试的竞态

全套测试中一项取消账本测试把子进程启动也算进500ms假设期限，重负载时尚未收到模拟503就超时。生产分类在此情形并无错误。测试现等待模拟服务确认两条 attempt 帧已发送，再用 mock timer 触发截止；保留原有失败身份、503、两次尝试与未知用量断言。未放宽生产取消语义。
