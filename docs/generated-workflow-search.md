# 模型生成工作流的自动调优

> 当前 npm 入口已切换至 [单次小批量自动搜索](small-batch-search.md)：16→32→64，每题一次，目标 F1 >90%。下文保留的是此前 200×5 协议的实现记录，不是当前运行设置。

本实验只优化生成提示词及 A/B 两种生成机制。具体节点、提示词、绑定和控制逻辑由 LLM 生成，不使用手工设计的解题候选。

- A：模型返回完整 JavaScript 模块，创建原生 Ditto Graph/Loop 和绑定函数。
- B：模型返回可序列化的图、控制与显式数据绑定定义，由固定执行器运行。
- 两路共用 `deepseek-flash`、固定生成配置、原生 Workers，以及 `locate_public_text` 和 `arithmetic` 通用工具。工具不包含题号、答案查找或解题流程。

在 Windows 项目目录运行：

```powershell
npm.cmd run experiment:drop
npm.cmd run experiment:drop:a
```

默认每路最多 3 个有效候选，每个候选使用完整 DROP 200 题验证集并重复 5 次；平均 F1 超过 0.85 后停止该路搜索。结构与运行失败不计入有效候选，另设工程尝试上限，全部失败及其资源消耗都保留。这里是验证集搜索，尚未执行冻结后的测试集评测。

优化器接收全部候选产物与评测摘要，再由白名单反馈构造器提供公开题面、预测、各次得分、配对改善/退化及评测成本。它不会接收标准答案、私有评测错误、私有断言或测试集结果。每次提案的公开修改说明由模型生成。

产物位于 `runs/generated-search/drop/`：

- `proposals/`：完整模型请求、原始响应与校验错误，便于核对候选来源。
- `candidates/`：模型生成的原始 A 源码或 B 定义。
- `checkpoints/`：实际生成的图与节点。A 的控制逻辑标记为代码控制，不伪造静态分支。
- `evaluations/`：完整验证结果及实际 Graph 执行轨迹。
- `optimizer-usage.json`：优化器调用资源；与候选验证成本分开记录。
- `workflow-report.png`：每个候选完成后更新的流程图，包含各次分数、调用数、Token 和耗时。

`work/manual-archive/` 和 `runs/native-drop/` 是此前偏离范围的手工实验记录，不进入自动搜索历史、示例或最佳候选选择。

遇到 HTTP 401/402/403 会停止搜索，保留成功题次。恢复时使用 `--resume-run <原目录> --resume-candidate <原候选id>`，校验相同模型、参数、表示方式、固定数据身份和重复次数，然后只重跑未成功的题次。原失败消耗仍保留，不会把余额错误当作答题错误交给优化器。

表示方式对比需要同时查看质量、合法率、工程失败、调用成本和耗时；一次成功候选不能证明哪种表示普遍更好。A 的 VM 和语法限制属于工程校验，不构成操作系统安全隔离。
